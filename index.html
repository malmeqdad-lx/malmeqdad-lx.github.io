01  Guided commerce

A shopping assistant that asks why before it recommends

A global consumer electronics retailer wanted a website chatbot that could do more than keyword search — it needed to shop the way a good in-store associate does, by understanding what a customer actually needs before suggesting anything.

Approach

  • Mapped a consultative sales conversation into a flexible slot-filling flow: why they're shopping, what's not working with what they have, which features would fix that, and any remaining preferences — answerable in any order, not a rigid script.
  • Wrote the assistant's persona and behavior prompt from scratch: tone, voice, and a strict output contract pairing a natural-language reply with a machine-readable product list, so the model's output was always predictable downstream.
  • Designed two function-call contracts — one to search inventory, one to pull full product detail — so every recommendation stayed grounded in real data instead of the model inventing specs.
  • Wrote reference conversations covering the happy path and the edge cases (budget pushback, feature comparisons, out-of-stock items) so engineering had a concrete target for the model's behavior before a line of code was written.

A shortened example

Shopper

I need new headphones for work calls.

Assistant

Happy to help. What's not working with your current pair, if you don't mind me asking?

Shopper

People keep saying they can't hear me in noisy rooms.

Assistant

That's a common one. In-ear or over-ear, and does a boom mic bother you?

Shopper

In-ear, and no boom mic please.

Assistant

Got it — here's a pair built around call-focused noise cancellation in a compact in-ear fit, which lines up with the noisy-room problem you mentioned.

Shopper

What if I want to spend less?

Assistant

This option keeps the same call-focused noise cancellation and drops the wireless charging case to bring the price down.

The client's own goal for the project: improve customer satisfaction, reduce operational cost, and grow sales — rolled out in phases rather than as a single launch.

Demonstrates: system prompt & persona design, function-calling contracts, ready-to-implement conversation specifications

02  Multi-step booking

Booking a trip without a form pretending to be a conversation

A large organization needed an assistant that could book flights, hotels, and ground transportation end to end, then route the approvals and reporting that come after, without making employees fill out what was really a form disguised as a chat.

Approach

  • Built a slot-filling architecture that accepts multiple details in one utterance (“a flight and a hotel to the coast next week”) instead of one question at a time.
  • Carried context across the booking sequence — flight dates informed the hotel date suggestions by default — so the system used what it already knew rather than re-asking.
  • Gave every capture point its own recovery path for low-confidence or unrecognized input, rather than one generic fallback for the whole flow.
  • Extended the design past booking into approval routing and post-trip reporting, so the conversation didn't end where the transaction did.

Demonstrates: multi-turn dialogue architecture, context carryover, error recovery, graceful fallback strategies

03  Evaluation & calibration

Catching the responses that are correct and still wrong

A multi-agent conversational AI system for a major financial services firm needed a way to catch responses that were technically accurate but pragmatically off — the wrong register, the wrong tone — before that gap showed up in production.

Approach

  • Built an evaluation rubric grounded in speech-act theory that scores register, tone, and pragmatic appropriateness, alongside deterministic metrics like routing and disambiguation accuracy.
  • Designed and ran the calibration process that kept several reviewers scoring consistently against that rubric.
  • Ran a multi-provider LLM evaluation across five model providers, building golden test sets and a scoring methodology from scratch to guide production model selection.
  • Mined production conversations to build Monte Carlo simulations that stress-tested a newly launched voice channel before it went live.

Demonstrates: evaluation rubric design, calibration process, model selection, pre-production quality testing

04  Guardrails on generative output

Letting a model answer only once it's earned the right to

An enterprise support assistant needed a generative layer for open-ended questions the rules-based flows couldn't cover, without letting ungrounded model output reach users unchecked.

Approach

  • Designed a confidence-gated handoff: known intents are handled deterministically, and only low-confidence matches escalate to retrieval-grounded generation, with a distinct path for when even that search comes up empty.
  • Specified a visible disclaimer pattern so people always know when a response was AI-generated versus pulled from a verified source.
  • Designed escalating fallback behavior — a first misunderstood turn gets a targeted reprompt, a second gets an offer to rephrase or hand off — so a repeat failure doesn't feel like hitting the same wall twice.
  • Set explicit scope boundaries on generative responses so the design anticipated where people would push past what the assistant was meant to handle, and routed accordingly.

Demonstrates: guardrail design, generated-content disclosure, escalating fallback, risk-aware scoping
